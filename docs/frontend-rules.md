# Правила вёрстки

Дальше в задачах на вёрстку эти правила упоминаются фразой «по правилам из docs/frontend-rules.md».

## 1. Чем верстаем

Обычные HTML, CSS и JS. Без сборщиков, без фреймворков, без npm-пакетов — так же, как сделан черновой фронт в `web/`. Причина та же, что и на бэкенде: ноль зависимостей означает, что проект запускается на чистой машине одной командой и не ломается от чужого обновления.

## 2. Один экран — одна страница

Один экран прототипа — один файл в папке `web/`. Никаких «страница, которая умеет пять экранов по адресной строке». Плановые имена файлов перечислены в карте экранов.

## 3. Запросы к серверу — только через `web/js/api.js`

Внутри страниц запросов быть не должно: ни `fetch`, ни `XMLHttpRequest`. Страница вызывает функцию из общего файла. Так пропуск, заголовки и разбор ошибок живут в одном месте, а не в шести.

## 3.1. Сессию ставит сервер, интерфейс её не трогает

Пропуск приезжает кукой с признаком `HttpOnly`: скрипты страницы её не читают, а браузер сам присылает с каждым запросом. Поэтому в коде интерфейса не должно быть ни `localStorage`, ни заголовка `Authorization`, ни разбора `document.cookie`.

Проверяется просто: F12 → Application → Local Storage. Пусто — значит правило соблюдено.

Отсюда же один порт: страницы и API отдаёт один процесс. Кука привязана к источнику, и при разных портах браузер её не пришлёт.

## 3.2. Никаких инлайновых скриптов и стилей

Страницы отдаются с политикой безопасности, где разрешены только собственные файлы. `<script>` с кодом внутри страницы и атрибут `style="…"` браузер выполнять откажется — код экрана живёт в `web/js/<экран>.js`, оформление в `web/css/`.

## 4. Цвета, шрифты и размеры — только из `web/tokens.css`

Никаких `#fff`, `14px` и `Arial` прямо в стилях страницы. Всё берётся переменными: `var(--color-text)`, `var(--space-4)`, `var(--radius-md)`.

Новых значений не добавляем. Если нужного оттенка или размера в токенах нет — это повод спросить, а не подобрать похожий на глаз. Токены собраны из дизайн-системы прототипа, и в них уже есть роли для текста, фона, границ, кнопок, ошибок и успеха.

## 5. Папку `server` не трогаем

Бэкенд готов и проверен. Если экрану не хватает данных — сначала говорим об этом, и только потом что-то делаем. Решение записывается в карту экранов, в раздел расхождений.

## 6. Папку «Прототип» не меняем

`site/` — образец. Не редактируем, не переименовываем, не удаляем, не переносим. Из неё только смотрят и копируют значения.

## 7. Ошибку от API показываем клиенту текстом на экране

Не только в консоли. Отказ сервера — это то единственное, что видит человек: если экран промолчал, он решит, что сломалось всё, и уйдёт. Показываем текст сообщения, которое прислал сервер.

Отдельно разбираются два случая:

- **409 «время занято»** — сервер присылает ближайшие свободные окна, показываем их кнопками, нажатие подставляет время;
- **сервер недоступен** — так и пишем, а надпись «Загрузка…» убираем: врать, что данные едут, нельзя.

Ошибки первой загрузки страницы обрабатываются так же, как ошибки по нажатию, — это отдельная ловушка, на ней уже спотыкались (журнал разработки, раздел 19).

## 8. Админ-панель верстаем, кабинет мастера — пока нет

Клиентские экраны и административные: каркас панели, записи студии, услуги, мастера, расписание, настройки, страница отказа. Кабинет мастера — следующий заход.

Правила у админки те же, что у клиентской части: токены из `web/tokens.css`, запросы через `web/js/api.js`, один экран прототипа — одна страница. Панель — часть сервиса, а не отдельный продукт: свой шрифт или своя палитра здесь считаются ошибкой, а не оформительским решением.

Отличается одно — доступ.

- **Раздел `/admin` закрывает сервер.** Проверяются вход и роль, каждая отдельно: гостя уводит на `/login`, вошедшую клиентку встречает 403. Проверка живёт в одном месте, через которое проходят все административные запросы, — новый адрес получает защиту сам, без копирования кода в каждый обработчик.
- **Скрытая ссылка — не защита.** Пункт меню от клиентки прячем: показывать ей там нечего. Но полагаться на это нельзя, адрес вводится руками.
- **Роли приходят списком.** Проверяем, есть ли у человека роль `admin`, а не равна ли его роль администратору. Владелица студии одновременно администратор и мастер — сравнение на равенство её не пропустит.
- **Роль не приходит из браузера.** Ни в теле запроса, ни в заголовке, ни в адресе: значение, отправленное страницей, контролирует тот, кто сидит за страницей. Сервер берёт роли из базы по пропуску.
- **Административную роль нельзя выдать себе.** Ни галочки в регистрации, ни экрана назначения, ни адреса. `admin` ставится только в базе.
- **Отказ показываем текстом.** Отдельная страница «Этот раздел только для администраторов» со ссылкой в кабинет — это то же правило 7, просто для кода 403: пустой экран и вечная «Загрузка…» не годятся.

Вход остаётся один. Второй формы авторизации по адресу вроде `/admin/login` не заводим: куда вести человека после входа, решают его роли из базы, а не адрес, по которому он открыл форму.

## 9. Что ещё держать в голове

- Время API отдаёт и принимает строкой UTC, заканчивающейся на `Z`. Показываем по часовому поясу студии — он приходит в `GET /api/studio`. Своей арифметики с поясами на экране не заводим.
- Деньги приходят целым числом копеек. Делит на сто и ставит знак рубля только вывод.
- Свободное время считает сервер. Экран его показывает и не пересчитывает.
- Права проверяет сервер. Скрытая кнопка — это удобство, а не защита: спрятать раздел можно, но полагаться на это нельзя.
- Фронтенд ничего не хранит, кроме пропуска. Всё остальное живёт в базе на сервере.

Пять минут чтения экономят вечер на выяснение, что данных для блока просто нет.
