# Требования к окружению и перенос на сервер

Документ отвечает на один вопрос: что должно быть на сервере, чтобы сервис запустился с первого раза и не упал через неделю.

## Требования

| Что | Значение | Почему именно так |
|---|---|---|
| Node.js | **минимум 22.13.0**, рекомендуется **24 LTS** | Ниже 22.13 модуль `node:sqlite` требует флага `--experimental-sqlite`, а до 22.5 его нет вовсе |
| SQLite | минимум 3.31 | Встроен в Node, отдельно не ставится. На генерируемых столбцах держится `appointments.ends_at` |
| Диск | локальный, каталог базы доступен на запись | Режим WAL создаёт рядом файлы `-wal` и `-shm` |
| Внешние пакеты | нет | Зависимостей у сервера нет: `node_modules` пуст, `npm ci` не нужен |

Версия закреплена в трёх местах: `.nvmrc` (24.19.0), поле `engines` в `server/package.json` и константы в `server/src/env-check.js`. При расхождении источник истины — `env-check.js`: только он проверяется во время работы.

## Проверка перед запуском

```bash
cd server && npm run doctor
```

Показывает версии, путь к базе, режим журнала, состояние внешних ключей, список применённых миграций и результат проверки целостности файла. Если окружение непригодно, команда падает с объяснением, что именно не так.

Часть проверок выполняется при каждом старте, до открытия базы, — они в `server/src/db.js` через `env-check.js`:

1. Версия Node не ниже минимальной. Иначе — отказ с указанием, чего не хватает.
2. Модуль `node:sqlite` есть в этой сборке и содержит `DatabaseSync`.
3. Каталог базы существует и доступен на запись.
4. После открытия: версия SQLite, `foreign_keys = ON`, режим журнала.

Мажорная версия Node, отличная от 24, работу не блокирует, но выводит предупреждение в лог.

## Порядок развёртывания

```bash
git clone <репозиторий> && cd nails
cp .env.example .env          # заполнить значения
cd server
npm run doctor                # проверка окружения
npm run migrate               # создание схемы
npm run seed                  # только для стенда, не для боевой установки
```

Миграции прогоняются **до** старта приложения, отдельным шагом. Каждый файл выполняется в своей транзакции, применённые отмечаются в `schema_migrations`, повторный запуск ничего не переделывает.

## Что может пойти не так

### Версия Node на сервере

Самый вероятный источник проблем. `apt install nodejs` в Debian и Ubuntu ставит версию из репозитория дистрибутива — она может оказаться и 18-й, и 20-й, где `node:sqlite` отсутствует полностью. Ставить нужно официальную сборку с nodejs.org, через nvm или через репозиторий NodeSource.

**Отдельно**: Node можно собрать с ключом `--without-sqlite`, и часть пакетов дистрибутивов так и собрана. Тогда версия подходит, а модуля нет. Проверка `checkSqliteModule` ловит именно этот случай и говорит, что делать.

### Статус модуля

`node:sqlite` имеет уровень стабильности **1.2 — release candidate**. Он больше не требует флага и не считается сырым, но формально его API ещё может измениться в Node 26. Практический вывод: закрепить мажорную версию Node — через `.nvmrc`, образ контейнера или пакет — и обновлять её осознанно, а не автоматически.

### Права и каталог базы

Сервис пишет не только в файл базы, но и рядом с ним: WAL создаёт `varvara.db-wal` и `varvara.db-shm`. Поэтому право на запись нужно **каталогу**, а не файлу. Симптом при нехватке прав — `SQLITE_CANTOPEN` или молчаливый откат журнала в режим `delete`, что видно в выводе `npm run doctor`.

В контейнере каталог с базой должен быть примонтированным томом, иначе база исчезнет при перезапуске.

### Сетевые файловые системы

**Базу нельзя держать на NFS, SMB или сетевом диске.** Блокировки там работают ненадёжно, а WAL требует разделяемой памяти, которой по сети нет. Результат — повреждение файла, причём не сразу. Только локальный диск.

### Несколько процессов

В SQLite один писатель на базу. Если запустить сервис в несколько процессов (кластер PM2, несколько воркеров), записи выстроятся в очередь. Ожидание блокировки задано 5 секундами (`busy_timeout`), при превышении — ошибка `SQLITE_BUSY`.

Для студии с тремя мастерами это не проблема: записей единицы в час. Но масштабировать сервис горизонтально на SQLite нельзя — это осознанное ограничение выбранного решения, см. раздел 8 схемы, пункт 11.

Важно, что **защита от двойной записи при этом не страдает**: блокировка живёт на уровне файла, поэтому `BEGIN IMMEDIATE` работает и между процессами, а не только между запросами одного.

### Резервное копирование

Копировать файл базы обычным `cp` во время работы **нельзя** — в копию попадёт несогласованное состояние, потому что часть данных лежит в `-wal`. Правильный способ:

```bash
sqlite3 varvara.db "VACUUM INTO '/backup/varvara-$(date +%F).db'"
```

Либо остановить сервис перед копированием. Утилита `sqlite3` для этого ставится отдельно — на работу сервиса она не влияет.

### Часовой пояс сервера

На хранение не влияет: SQLite отдаёт `now` в UTC, а приложение пишет ISO-8601 с суффиксом `Z`. Но одно место зависит от пояса — значение по умолчанию `working_hours.valid_from` берётся как `strftime('%Y-%m-%d','now')`, то есть **дата по UTC**. Если строку графика создать ночью по московскому времени, дата начала действия окажется вчерашней. На расчёт свободных окон это не влияет, но при заполнении графика через панель дату лучше передавать явно.

### Сравнение строк без учёта регистра

`COLLATE NOCASE` в SQLite работает только для латиницы. Почта вида `Ivan@…` и `ivan@…` считается одинаковой, а кириллическая — нет. Для адресов почты это некритично: они латинские.

## Чего в этой установке нет

Пока в проекте только база: подключение, миграции и тестовые данные. Кода приложения, API и фронтенда нет, поэтому вопросы обратного прокси, TLS, автозапуска и журналирования решаются на следующем этапе.
