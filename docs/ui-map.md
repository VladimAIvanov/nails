# Карта «экран — эндпоинт»

Вторая карта проекта. Первая — [Карта связей](Карта%20связей.dc.html) — про переходы: какая кнопка на какой экран ведёт. Эта — про данные: откуда экран их берёт и какие адреса дёргают его кнопки.

Прототип не знает про API, API не знает про прототип. Здесь они сведены.

**Охват.** Клиентские экраны — лендинг, авторизация, запись, личный кабинет, профиль, уведомления, служебные страницы — и административные: каркас панели, записи студии, услуги, мастера, расписание, настройки, отказ в доступе. Кабинет мастера — следующий заход, он собирается отдельно от админки.

**Как читать.** «Данные» — что экран запрашивает при открытии. «Действия» — что вызывают его кнопки. «Переходы» — куда уводит с экрана. Имена страниц в колонке «Файл вёрстки» — плановые, папка `web/`.

Все адреса — из работающего API (101 адрес, `GET /api` отдаёт полный список). Время везде приходит строкой UTC с `Z`, деньги — целыми копейками.

## 3. Запись

Четыре шага. В прототипе они живут двумя способами: модалкой на лендинге и отдельными экранами мини-приложения (`site/Клиент.dc.html`, разметка — `site/assets/varvara-app.jsx`). Верстаем одной страницей с шагами.

| | |
|---|---|
| **Файл вёрстки** | `web/booking.html` |
| **Шаг 1 — услуга** | `GET /api/services` (карточки и чипы категорий) |
| **Шаг 2 — мастер** | `GET /api/masters?service_id=<id>` — кто делает выбранную услугу; `GET /api/masters/:id` — карточка мастера с его услугами, рейтингом и работами; `GET /api/masters/:id/reviews` — отзывы |
| **Шаг 3 — время** | `GET /api/masters/:id/slots?date=<YYYY-MM-DD>&service_id=<id>` — свободные окна на дату. Сервер считает их сам: рабочие часы, минус блокировки, чужие записи и живые удержания, шагом сетки, с учётом суммарной длительности услуг. Экран ничего не пересчитывает<br>`GET /api/studio` — часовой пояс студии для показа времени |
| **Шаг 3 — удержание** | «Выбрать окно» — `POST /api/holds` (мастер, услуги, время). Держит окно несколько минут, пока заполняются контакты; `GET /api/holds/:token` — сколько осталось; `DELETE /api/holds/:token` — отказ от удержания |
| **Шаг 4 — подтверждение** | «Записаться» — `POST /api/appointments` (master_id, service_ids, starts_at, comment, hold_token). Ответ 201 — карточка записи с номером |
| **Отказ «время занято»** | ответ 409 приходит с полем `details.available` — пять ближайших свободных окон. Показываем их кнопками: нажатие подставляет время и повторяет запись |
| **Экран «Готово»** | данные берутся из ответа `POST /api/appointments`, повторных запросов нет |
| **Переходы** | «Мои записи» → кабинет, «Закрыть» → лендинг |
| **Чего не будет** | кнопки «Любой свободный мастер» — см. расхождение №2 |

## 7. Админ-панель: каркас и доступ

| | |
|---|---|
| **Прототип** | `site/Админ-панель.dc.html` (разметка — `site/assets/varvara-admin.jsx`, компоненты `Sidebar` и `AdminApp`) |
| **Файл вёрстки** | `web/admin/index.html`; общий код шапки и меню — `web/js/admin.js`, оформление — `web/css/admin.css` |
| **Что показывает** | боковое меню «Записи», «Услуги», «Мастера»; шапку с названием открытого раздела и подписью «Варвара · админ-панель» с именем вошедшего |
| **Данные** | `GET /api/auth/me` — кто вошёл: имя и роли<br>`GET /api/studio` — название студии и часовой пояс: время на всех административных экранах показывается по нему |
| **Действия** | «Выйти» — `POST /api/auth/logout` |
| **Переходы** | → «Записи» (`/admin`), → «Услуги» (`/admin/services`), → «Мастера» (`/admin/masters`). В клиентской шапке пункт «Админ-панель» показывается только тем, у кого есть роль `admin` |
| **Чего не будет** | переключателя «Показать как: Владелица / Лена · мастер». В прототипе это орган управления макетом, а не экран: роли приходят из базы, и выбрать их в браузере нельзя |

Отдельного входа у раздела нет. Форма `/login` одна на всех: сервер узнаёт человека, читает его роли и отправляет клиентку в кабинет, а администратора — в `/admin`. Вторая форма не сделала бы раздел безопаснее, зато восстановление и смену пароля пришлось бы держать в двух местах.

Адрес `/admin` открывает `web/admin/index.html`: отдача страниц ищет `<путь>/index.html` раньше, чем `<путь>.html` (`server/src/static.js`). Поэтому раздел лежит одной папкой, а адреса остаются без расширений.

**Доступ.** Роль `admin`, проверяет сервер. Гостя `/admin` уводит на `/login`, клиентку встречает 403 и страница отказа. Скрытый пункт меню — удобство, а не защита: адрес можно ввести руками.

## 8. Записи студии

| | |
|---|---|
| **Прототип** | `site/Админ-панель.dc.html`, экран «Записи» (компонент `ListView`) |
| **Файл вёрстки** | `web/admin/index.html` |
| **Что показывает** | сводку сверху — всего записей, сколько ждут подтверждения, ожидаемая выручка; таблицу: когда, клиентка с телефоном, услуга, мастер, сумма, источник, статус |
| **Данные** | `GET /api/admin/appointments` — записи всех клиенток студии, а не только свои. Фильтры строкой запроса: `status`, `date`, `master_id`, `search` (имя или телефон), `limit` (по умолчанию 50, максимум 200). Блок `summary` в ответе — те самые числа сводки, считать их на экране не нужно<br>`GET /api/admin/masters` — список для фильтра по мастеру<br>`GET /api/studio` — часовой пояс |
| **Действия** | «Подтвердить» у записи со статусом `pending` — `POST /api/admin/appointments/:id/confirm`<br>«Отменить» с причиной — `POST /api/appointments/:id/cancel`: строка остаётся в списке со статусом «отменена», время освобождается<br>«Перенести» — свободные окна из `GET /api/masters/:id/slots`, затем `PATCH /api/appointments/:id`. Меняется время у той же записи, второй строки не появляется<br>«Записать клиента» — `POST /api/admin/appointments`; при пересечении сервер отвечает 409 со списком свободных окон, и только по отдельному подтверждению запрос повторяется с `allow_overlap: true`<br>«Заблокировать время» — `POST /api/admin/time-off`, снять — `DELETE /api/admin/time-off/:id`<br>поиск клиентки при оформлении — `GET /api/admin/clients?search=`<br>переключение дат и фильтр по мастеру — повторный `GET /api/admin/appointments` |
| **Переходы** | → «Услуги», → «Мастера» пунктами меню |
| **Чего не будет** | колонки «Мастер» в кабинете мастера: там `GET /api/master/appointments` отдаёт только свои записи. Это другой экран и другой заход |

Правило владения здесь другое, чем у клиентки. `GET /api/appointments/my` отдаёт только свои записи и отвечает 403 на чужой номер; `GET /api/admin/appointments` отдаёт все. Это не отсутствие проверки, а вторая ветка того же правила, и записана она в самом адресе.

## Расхождения: клиентскому экрану не хватает данных

Правило: бэкенд сейчас не трогаем, решаем на стороне экрана.

| Находка | Решение | Почему |
|---|---|---|
| **1. Восстановление пароля.** Группа «Авторизация» предполагает экран, но в API нет ни одного адреса для сброса пароля по телефону или почте | **Убрать из вёрстки.** В форме входа оставить строку: «Забыли пароль — напишите в студию, вам помогут войти» | Сброс пароля требует канала подтверждения — письма или кода в Telegram. | **2. «Любой свободный мастер».** В прототипе мини-приложения есть такая кнопка, а `POST /api/appointments` требует `master_id` | **Собрать из нескольких запросов.** Экран запрашивает окна у всех мастеров услуги (`GET /api/masters?service_id=…`, затем `GET /api/masters/:id/slots` по каждому), показывает объединённый список и при выборе окна подставляет того мастера, у кого оно свободно | В базе есть поле `master_auto_assigned`, но адреса автоподбора нет. | **3. История смены статусов в карточке записи.** `GET /api/appointments/:id` отдаёт поле `history` только мастеру и администратору | **Убрать элемент из вёрстки** клиентского кабинета | Это служебный след для студии. Клиентке достаточно текущего статуса, а показать чужое поле всё равно не дадут — сервер его просто не пришлёт |
| **4. Журнал отправленных уведомлений** («Отправлено», «Не доставлено», «вчера 19:02») из `site/Уведомления и регулярные записи.dc.html` | **Решено иначе, см. раздел 10а.** Журнал доставки клиентке по-прежнему не показываем: очередь `GET /api/admin/notifications/due` — дело студии. Вместо него собран список сообщений о том, что студия сделала с её записями | Клиентке важно не «доставлено ли письмо», а «что случилось с моим визитом». | **5. Кнопка «Повторить» в истории визитов** — отдельного адреса нет | **Собрать из существующих.** Карточка уже содержит `master.id` и `service.id`; кнопка ведёт на `booking.html?master_id=…&service_id=…`, дальше обычный сценарий записи | Повтор — это не новое действие сервера, а та же запись с заполненными полями |

Если отзывов ноль — блок не показываем |
| **11. Занятые окна в сетке дня.** `GET /api/masters/:id/slots` отдаёт только свободные, а прототип показывает занятое время видимым и неактивным | **Можно собрать из нескольких запросов.** Сетка дня строится из `working_hours` студии (`GET /api/studio`) и шага сетки `step_min` из того же ответа; свободные — те, что назвал сервер, остальные показываются занятыми | Прятать занятое нельзя: клиентка, видевшая окно в 15:00 минуту назад, не поймёт, куда оно делось. Расчёт по-прежнему на сервере — экран лишь достраивает разметку сетки |
| **12. | **13. Экран успеха при нескольких услугах.** Сервер сохраняет несколько записей подряд, по одной на услугу | **Данные в API есть.** `POST /api/appointments` возвращает список записей — экран показывает их все и общий итог | Это не ошибка, а устройство сервиса: у каждой услуги свой номер, статус и цена |

## Чего нельзя решить на стороне клиентского экрана

Здесь ничего не придумано — просто названо.

1. **Восстановление пароля.** Нужен адрес, который отправит код или ссылку в Telegram, на почту или SMS, и второй, который примет новый пароль. Без бэкенда не делается.
2. **Средняя оценка студии одним числом.** Считать её на экране можно, но это будет среднее по мастерам, а не по визитам. Точное значение даёт только запрос к базе.
3. **Автоподбор мастера при записи.** Экран может перебрать мастеров, но при высокой нагрузке между перебором и записью окно успеют занять. Настоящий автоподбор — это один запрос, который выбирает и записывает в одной транзакции.
4. **Хранилище картинок.** В API есть поля `image_url`, но файлов нет и загружать их некуда.
5. **Журнал доставки уведомлений для клиентки.** Очередь видна только администратору.

## Расхождения: административному экрану не хватает данных

Нумерация с буквой «А», чтобы не путать с клиентскими. Правило прежнее: бэкенд не трогаем, решение — на стороне экрана; чего нельзя решить на экране, просто называем.

| Находка | Решение | Почему |
|---|---|---|
| **А1. Роли вошедшего не приходят в интерфейс.** `POST /api/auth/login` и `GET /api/auth/me` отдают одно поле `role` — основную роль. Список ролей сервер собирает (`rolesOf` в `server/src/auth.js`) и проверяет им права, но наружу не отдаёт. Проверено запросом: ответ `{"user":{"id":1,"role":"admin",…}}`, поля `roles` нет | **Исправлено на сервере.** `POST /api/auth/login` и `GET /api/auth/me` отдают полный список `roles` рядом с основной `role`. Обходной путь — пробный запрос за 403 — не понадобился | Это упиралось в перенаправление после входа: без ролей интерфейс не знает, вести человека в кабинет или в `/admin`. Владелица студии и администратор, и мастер — с одним полем `role` отличить её от обычного мастера нельзя. Список ничего не разрешает: права сервер по-прежнему проверяет сам, по базе |
| **А2. Занятость мастера одним ответом не собрать.** Экран «Расписание» рисует сетку дня по колонкам мастеров. Записи есть в `GET /api/admin/appointments?date=`, часы — в `GET /api/admin/working-hours`, отпуска и блокировки — в `/api/admin/time-off` и `/api/admin/schedule-exceptions`, но одного адреса «день мастера целиком» нет | **Собрать из нескольких запросов.** Четыре запроса при открытии экрана, сетка строится из часов студии, поверх кладутся записи, отпуска и исключения | Каждый кусок данных в API есть, не хватает только сборки. Считать занятость экран по-прежнему не будет — он раскладывает то, что прислал сервер |
| **А3. Плитка «свободных окна».** `summary` в `GET /api/admin/appointments` даёт «всего», «ждут подтверждения» и ожидаемую выручку. Числа свободных окон в нём нет | **Убрать плитку** из первой версии экрана расписания | Считать её на экране — значит повторить логику слотов, которая живёт на сервере: рабочие часы минус блокировки, чужие записи и живые удержания. Повторённый расчёт разойдётся с настоящим |
| **А4. Экрана «Мастера» в прототипе нет.** API для управления мастерами полный, а образца вёрстки нет: в макете мастера только колонки расписания и чипы переключателя | **Собрать по образцу «Услуг».** Те же карточки со списком слева и формой добавления справа | Оба экрана — список однотипных записей с формой. Придумывать для мастеров отдельный язык интерфейса незачем |
| **А5. Услуги конкретного мастера.** `GET /api/admin/masters` отдавал только счётчик `services_count` | **Исправлено на сервере.** Тот же адрес отдаёт `service_ids` рядом со счётчиком | Клиентский `GET /api/masters/:id` не подошёл: он не показывает услуги, снятые с публикации, а за мастером они всё равно закреплены. Экран правки терял бы отметки |
| **А6. Подключение Telegram-бота.** Экран «Настройки» показывает «@varvara_nails_bot · подключён» и кнопку «Настроить бота». В `GET /api/admin/settings` есть `telegram_bot_username` и `bot_status`, но адреса, который бота подключает, в API нет | **Показать состояние, кнопку убрать.** Имя бота и `bot_status` выводим как есть | Подключение бота — это обмен токенами с Telegram, работа бэкенда. На экране её не придумать |
| **А7. Фотографии работ и аватары мастеров.** То же, что и в клиентской части: поля `image_url` в API есть, файлов и хранилища нет | **Рамка-заглушка с подписью**, как в прототипе | Загружать некуда, адреса приёма файла в API нет |

### Чего нельзя решить на стороне административного экрана

1. **Число свободных окон за день.** Считает только сервер — по тем же правилам, по которым выдаёт слоты клиентке.
2. **Подключение бота.**
3. **Хранилище картинок.**

## Расхождения: административный эндпоинт без экрана

| Находка | Решение | Почему |
|---|---|---|
| `GET /api/admin/appointments`, `POST`, `POST /:id/confirm` — записи студии | **Сделано в этом заходе.** Экран «Записи»; оформление визита и наложение поверх занятого времени — на экране расписания | Это главный экран администратора: с него начинается день |
| `GET/POST/PATCH/DELETE /api/admin/services`, `POST /api/admin/categories`, `DELETE /api/admin/categories/:id` — услуги и категории | **Сделано в этом заходе.** Экран «Услуги» | Прайс правит владелица, а не разработчик миграцией |
| `GET/POST/PATCH/DELETE /api/admin/masters` — мастера | **Сделано в этом заходе.** Экран «Мастера», собран по образцу «Услуг» (расхождение А4) | Без него нового мастера заводят прямо в базе |
| `GET/PUT /api/admin/working-hours`, `GET/POST/DELETE /api/admin/schedule-exceptions`, `GET/POST/DELETE /api/admin/time-off` — график, исключения, отпуска | **Следующий заход.** Экран «Расписание» и раздел часов работы в настройках | Расписание — самый плотный экран панели, его собираем отдельно |
| `GET/PATCH /api/admin/settings` — настройки студии | **Следующий заход.** Экран «Настройки» | Переключатели онлайн-записи и ручного подтверждения меняют поведение всего сервиса |
| `GET /api/admin/clients` — поиск клиентки по имени и телефону | **Добавить в существующий экран.** Поле поиска в форме оформления записи администратором | Своего экрана не заслуживает: это подсказка внутри другой формы |
| `POST /api/admin/appointments/:id/deposit` — отметка о депозите | **Добавить в существующий экран.** Кнопка в карточке записи | Деньги принимает касса, сюда попадает только отметка |
| `PATCH /api/admin/content/:slug`, `POST/DELETE /api/admin/portfolio` — тексты лендинга и работы | **Следующий заход.** Раздел в настройках | Прототип этих экранов не рисует: правку контента студия делает редко |
| `GET /api/admin/notifications/due`, `POST /api/admin/notifications/:id/sent` — очередь уведомлений | **Экрана пока не будет.** Тот самый журнал доставки, который убрали из клиентского профиля (расхождение №4) | Очередь разбирает отправщик, а не человек. Экран понадобится, когда появится ручная переотправка |
| `GET/POST /api/admin/materials`, `POST /api/admin/materials/:id/movement`, `PUT /api/admin/services/:id/materials` — материалы и их списание | **Экрана пока не будет.** В прототипе склада нет | Учёт расходников — отдельный сценарий, к записи клиенток он не относится |
| `GET /api/admin/payroll`, `GET /api/admin/analytics` — выплаты и аналитика | **Экрана пока не будет.** Оба требуют обязательные `from` и `to` — проверено запросом без параметров, ответ 400 | В прототипе нет ни отчётов, ни графиков. Придумывать их поверх API — работа отдельного захода |
| `POST /api/master/appointments`, `POST /api/master/appointments/:id/confirm`, `GET /api/master/appointments` — кабинет мастера | **Следующий заход.** В прототипе он есть: тот же макет с урезанным меню «Моё расписание» и «Мои записи» | Мастер видит только свои записи — это третья ветка правила владения, и её лучше собирать отдельно от админки |
