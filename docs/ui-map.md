# Карта «экран — эндпоинт»

Вторая карта проекта. Первая — [Карта связей](Карта%20связей.dc.html) — про переходы: какая кнопка на какой экран ведёт. Эта — про данные: откуда экран их берёт и какие адреса дёргают его кнопки.

Прототип не знает про API, API не знает про прототип. Здесь они сведены.

**Охват.** Только клиентские экраны: лендинг, авторизация, запись, личный кабинет, профиль, уведомления, служебные страницы. Экраны мастера и администратора — позже, отдельной картой.

**Как читать.** «Данные» — что экран запрашивает при открытии. «Действия» — что вызывают его кнопки. «Переходы» — куда уводит с экрана. Имена страниц в колонке «Файл вёрстки» — плановые, папка `web/`.

Все адреса — из работающего API (101 адрес, `GET /api` отдаёт полный список). Время везде приходит строкой UTC с `Z`, деньги — целыми копейками.

## 2. Авторизация

| | |
|---|---|
| **Прототип** | `site/Вход.dc.html` |
| **Файл вёрстки** | `web/login.html` |
| **Что показывает** | форму входа (телефон или почта + пароль) и форму регистрации клиентки с согласием на обработку данных |
| **Данные** | ничего не запрашивает при открытии |
| **Действия** | «Войти» — `POST /api/auth/login`, в ответ пропуск и срок его действия<br>«Зарегистрироваться» — `POST /api/auth/register` (имя, телефон, пароль, согласие; почта необязательна)<br>«Выйти» в шапке любого экрана — `POST /api/auth/logout`<br>проверка сеанса при открытии защищённых страниц — `GET /api/auth/me` |
| **Переходы** | после входа роль `client` → кабинет; после регистрации → кабинет; «Записаться» → запись |
| **Чего не будет** | формы восстановления пароля — в API такого адреса нет, см. расхождение №1. Вместо неё страница `/password-reset` объясняет, что делать: контакты студии из `GET /api/studio` и переход к смене пароля для тех, кто вошёл (`/password-change`, `POST /api/profile/password`) |

Роль в запросе не принимается: регистрация всегда создаёт клиентку. Экран «Вы: клиент / мастер / администратор» в прототипе — переключатель макета, а не форма; в вёрстке его нет.

## 3. Запись

Четыре шага. В прототипе они живут двумя способами: модалкой на лендинге и отдельными экранами мини-приложения (`site/Клиент.dc.html`, разметка — `site/assets/varvara-app.jsx`). Верстаем одной страницей с шагами.

| | |
|---|---|
| **Файл вёрстки** | `web/booking.html` |
| **Шаг 1 — услуга** | `GET /api/services` (карточки и чипы категорий) |
| **Шаг 2 — мастер** | `GET /api/masters?service_id=<id>` — кто делает выбранную услугу; `GET /api/masters/:id` — карточка мастера с его услугами, рейтингом и работами; `GET /api/masters/:id/reviews` — отзывы |
| **Шаг 3 — время** | `GET /api/masters/:id/slots?date=<YYYY-MM-DD>&service_id=<id>` — свободные окна на дату. Сервер считает их сам: рабочие часы, минус блокировки, чужие записи и живые удержания, шагом сетки, с учётом суммарной длительности услуг. Экран ничего не пересчитывает<br>`GET /api/studio` — часовой пояс студии для показа времени |
| **Шаг 3 — удержание** | «Выбрать окно» — `POST /api/holds` (мастер, услуги, время). Держит окно несколько минут, пока заполняются контакты; `GET /api/holds/:token` — сколько осталось; `DELETE /api/holds/:token` — отказ от удержания |
| **Шаг 4 — подтверждение** | «Записаться» — `POST /api/appointments` (master_id, service_ids, starts_at, comment, hold_token). Ответ 201 — карточка записи с номером |
| **Отказ «время занято»** | ответ 409 приходит с полем `details.available` — пять ближайших свободных окон. Показываем их кнопками: нажатие подставляет время и повторяет запись |
| **Экран «Готово»** | данные берутся из ответа `POST /api/appointments`, повторных запросов нет |
| **Переходы** | «Мои записи» → кабинет, «Закрыть» → лендинг |
| **Чего не будет** | кнопки «Любой свободный мастер» — см. расхождение №2 |

## Расхождения: экрану не хватает данных

Правило: бэкенд сейчас не трогаем, решаем на стороне экрана.

| Находка | Решение | Почему |
|---|---|---|
| **1. Восстановление пароля.** Группа «Авторизация» предполагает экран, но в API нет ни одного адреса для сброса пароля по телефону или почте | **Убрать из вёрстки.** В форме входа оставить строку: «Забыли пароль — напишите в студию, вам помогут войти» | Сброс пароля требует канала подтверждения — письма или кода в Telegram. Это работа бэкенда, придумать её на стороне экрана нельзя |
| **2. «Любой свободный мастер».** В прототипе мини-приложения есть такая кнопка, а `POST /api/appointments` требует `master_id` | **Собрать из нескольких запросов.** Экран запрашивает окна у всех мастеров услуги (`GET /api/masters?service_id=…`, затем `GET /api/masters/:id/slots` по каждому), показывает объединённый список и при выборе окна подставляет того мастера, у кого оно свободно | В базе есть поле `master_auto_assigned`, но адреса автоподбора нет. Экран может выбрать мастера сам — сервер всё равно проверит занятость |
| **3. История смены статусов в карточке записи.** `GET /api/appointments/:id` отдаёт поле `history` только мастеру и администратору | **Убрать элемент из вёрстки** клиентского кабинета | Это служебный след для студии. Клиентке достаточно текущего статуса, а показать чужое поле всё равно не дадут — сервер его просто не пришлёт |
| **4. Журнал отправленных уведомлений** («Отправлено», «Не доставлено», «вчера 19:02») из `site/Уведомления и регулярные записи.dc.html` | **Убрать из клиентской вёрстки.** Оставить только переключатели каналов | Единственный адрес с очередью — `GET /api/admin/notifications/due` — административный. Экран доставки нужен студии, а не клиентке; вернётся вместе с админкой |
| **5. Кнопка «Повторить» в истории визитов** — отдельного адреса нет | **Собрать из существующих.** Карточка уже содержит `master.id` и `service.id`; кнопка ведёт на `booking.html?master_id=…&service_id=…`, дальше обычный сценарий записи | Повтор — это не новое действие сервера, а та же запись с заполненными полями |
| **6. Средняя оценка студии** «4.9 · 265 отзывов» в первом экране лендинга | **Собрать из нескольких запросов.** `GET /api/masters` отдаёт `rating` и `reviews_count` по каждому мастеру: среднее взвешенное по числу отзывов и их сумма | Агрегата по студии в API нет, но слагаемые есть. Если отзывов ноль — блок не показываем |
| **11. Занятые окна в сетке дня.** `GET /api/masters/:id/slots` отдаёт только свободные, а прототип показывает занятое время видимым и неактивным | **Можно собрать из нескольких запросов.** Сетка дня строится из `working_hours` студии (`GET /api/studio`) и шага сетки `step_min` из того же ответа; свободные — те, что назвал сервер, остальные показываются занятыми | Прятать занятое нельзя: клиентка, видевшая окно в 15:00 минуту назад, не поймёт, куда оно делось. Расчёт по-прежнему на сервере — экран лишь достраивает разметку сетки |
| **12. Сумма и общая длительность на шаге выбора услуг.** Сервер считает длительность визита только вместе с мастером — в ответе слотов | **Собрать из нескольких запросов.** На шаге услуг складываются цены и длительности, пришедшие в `GET /api/services`, с пометкой «без перерыва мастера»; точная длительность приходит от сервера на шаге времени (`duration_min`, `buffer_min`) и показывается там | Пока мастер не выбран, перерыв неизвестен никому, включая сервер. Честнее показать приблизительную сумму сразу и точную — когда она появится |
| **13. Экран успеха при нескольких услугах.** Сервер сохраняет несколько записей подряд, по одной на услугу | **Данные в API есть.** `POST /api/appointments` возвращает список записей — экран показывает их все и общий итог | Это не ошибка, а устройство сервиса: у каждой услуги свой номер, статус и цена |
| **7. Счётчик «2» на вкладке «Мои записи»** в мини-приложении | **Данные есть.** Длина массива `upcoming` из `GET /api/appointments/my?scope=upcoming` | Отдельный адрес для счётчика не нужен |
| **8. Текст «Ежедневно 10:00–21:00, воскресенье выходной»** в профиле | **Значение брать из API, текст привести к нему.** `GET /api/studio` отдаёт `working_hours` списком по дням недели; строку собирать из него, а не писать руками | Часы студии меняются в настройках. Захардкоженный текст рано или поздно разойдётся с расписанием |
| **9. Фотографии** — hero, работы, аватары мастеров | **Это не данные, а контент.** `GET /api/portfolio` и `GET /api/content` отдают `image_url`, но самих файлов в проекте нет | Хранилище картинок не поднято. Верстаем рамку-заглушку с подписью, как в прототипе |
| **10. Кнопка «Позвонить»** и ссылка на Telegram-бота | **Это не данные, а обычный контент страницы**, собранный из `GET /api/studio`: `phone` и `telegram_bot` | Достаточно ссылок `tel:` и `https://t.me/…` |

## Расхождения: эндпоинт без экрана

| Находка | Решение | Почему |
|---|---|---|
| `POST /api/waitlist`, `GET /api/waitlist`, `DELETE /api/waitlist/:id` — лист ожидания | **Добавить кнопку на существующий экран.** На шаге «Время», когда свободных окон нет: «Сообщить, если освободится» | Ради этого лист ожидания и заведён: отменённый визит иначе просто пропадает |
| `GET /api/passes`, `GET /api/passes/:id` — абонементы | **Экран будем верстать позже.** В кабинете отдельная вкладка «Абонементы» | Экрана в прототипе нет, придумывать его сейчас — гадать. Сценарий записи без него полон |
| `GET /api/loyalty`, `POST /api/loyalty/spend` — баллы | **Экран будем верстать позже.** Вместе с абонементами | То же самое: в прототипе не нарисовано |
| `POST /api/calendar/subscribe`, `DELETE`, `GET /api/calendar/:token` — подписка календаря | **Добавить кнопку на существующий экран** — в профиль, строкой «Добавить визиты в календарь» | Ленты не нужен свой экран, достаточно ссылки, которую человек копирует в приложение календаря |
| `GET /api/appointments/:id/calendar.ics` — один визит файлом | **Добавить кнопку на существующий экран** — в карточку записи в кабинете | Одна ссылка рядом с визитом, отдельная страница ни к чему |
| `POST /api/profile/password` — смена пароля | **Добавить кнопку на существующий экран** — раздел «Безопасность» в профиле | Форма из трёх полей помещается в профиль |
| `GET /api/profile/sessions`, `DELETE /api/profile/sessions/:id` — устройства и входы | **Добавить кнопку на существующий экран** — там же, в «Безопасности» | Список коротких строк, экрана не заслуживает |
| `POST /api/notifications/devices`, `DELETE /api/notifications/devices/:token` — регистрация устройства для пушей | **Оставить как есть.** Вызывается кодом страницы при разрешении на уведомления, кнопки не нужно | Это техническое действие браузера, человеку показывать нечего |
| `GET /api/profile/consents`, `POST /api/profile/consents` — согласия | **Добавить кнопку на существующий экран** — строка в профиле со ссылкой на политику и переключателем маркетинга | 152-ФЗ требует, чтобы человек видел, на что согласился, и мог отозвать |
| `POST /api/appointments/:id/review` — отзыв | **Добавить окно подтверждения.** После состоявшегося визита в карточке — «Оценить»: звёзды и поле текста | Отдельный экран ради одной оценки избыточен |
| `GET /api/masters/:id/reviews` — отзывы мастера | **Добавить кнопку на существующий экран** — раскрытие в карточке мастера на шаге выбора | Отзывы читают при выборе мастера, а не отдельно |
| `POST /api/recurring`, `GET`, `POST /api/recurring/:id/extend`, `DELETE` — регулярные записи | **Добавить кнопку на существующий экран** — блок в профиле, как нарисовано в прототипе уведомлений | Экран для этого в прототипе есть, но он совмещён с уведомлениями |
| `GET /api/holds/:token`, `DELETE /api/holds/:token` | **Оставить как есть.** Вызываются кодом страницы записи: проверка остатка времени и отказ от удержания при закрытии формы | Человек про удержание не думает, ему видно только «окно занято за вами» |
| `GET /api/health`, `GET /api` | **Оставить как есть.** Служебные, экрана не требуют | Первый — проверка живости, второй — список адресов для разработки |
| 39 адресов `/api/admin/*` и `/api/master/*` — записи студии, услуги, мастера, расписание, исключения, отпуска, категории, материалы, выплаты, аналитика, настройки, депозиты, содержимое лендинга, портфолио | **Экраны будем верстать позже.** Панель студии и кабинет мастера — следующий заход | По условию этого шага берём только клиента |
| `POST /api/appointments/:id/complete` — завершить визит; `GET /api/clients/:id/card` и `PATCH /api/clients/:id/card` — карточка клиентки; `PATCH /api/appointments/:id/note` — заметка мастера; `POST /api/appointments/:id/photos` — фото работы; `POST /api/passes` — выдать абонемент | **Экраны будем верстать позже.** Адрес не начинается с `/api/admin`, но права — мастера или администратора: клиентке эти адреса отвечают 403 | Это действия студии после визита. Проверено запросом клиентским пропуском — 403 |

## Чего нельзя решить на стороне экрана

Здесь ничего не придумано — просто названо.

1. **Восстановление пароля.** Нужен адрес, который отправит код или ссылку в Telegram, на почту или SMS, и второй, который примет новый пароль. Без бэкенда не делается.
2. **Средняя оценка студии одним числом.** Считать её на экране можно, но это будет среднее по мастерам, а не по визитам. Точное значение даёт только запрос к базе.
3. **Автоподбор мастера при записи.** Экран может перебрать мастеров, но при высокой нагрузке между перебором и записью окно успеют занять. Настоящий автоподбор — это один запрос, который выбирает и записывает в одной транзакции.
4. **Хранилище картинок.** В API есть поля `image_url`, но файлов нет и загружать их некуда.
5. **Журнал доставки уведомлений для клиентки.** Очередь видна только администратору.
