# Ноготочки — сервис онлайн-записи бьюти-студии

Клиентка выбирает услугу, мастера и свободное время и записывается сама; студия ведёт расписание, подтверждает и переносит визиты. Это учебный проект. Бэкенд, база и клиентский интерфейс готовы и приняты по чек-листу; админ-панель и кабинет мастера — следующая итерация.

Что лежит в репозитории:

| Папка | Что это |
|---|---|
| `server/` | API и база: Node.js + SQLite, **без единой внешней зависимости** |
| `web/` | интерфейс клиента: лендинг, авторизация, запись в четыре шага, кабинет; в `web/draft/` — черновая панель студии до сборки админки |
| `site/` | прототип интерфейса (артефакт проектирования, кодом не используется) |
| `docs/` | схема базы, журнал разработки, требования к развёртыванию, паспорт продукта |

## Что нужно установить

**Node.js версии 22.13 или новее.** Рекомендуется 24 LTS — на нём проект разрабатывался, версия закреплена в `.nvmrc`. Скачать: <https://nodejs.org>.

Почему именно эта версия: база работает через встроенный модуль `node:sqlite`, который перестал требовать особый флаг только в 22.13.

**Git** — чтобы забрать репозиторий: <https://git-scm.com>.

Больше ничего. Отдельную СУБД ставить не нужно: SQLite встроен в Node, база — один файл. `npm install` выполнять тоже не нужно: зависимостей у проекта нет.

Проверить, что Node на месте:

```bash
node --version
```

Ответ должен начинаться с `v22.13` или выше.

## Запуск за пять шагов

### 1. Забрать репозиторий

```bash
git clone https://github.com/VladimAIvanov/nails.git
```

```bash
cd nails
```

### 2. Создать базу

```bash
cd server && npm run migrate
```

Появится файл `server/data/varvara.db` и применённые миграции. В репозиторий он не попадает — база всегда создаётся на месте.

### 3. Загрузить демонстрационные данные

```bash
SEED_SHOW_PASSWORDS=true npm run seed
```

Появятся 6 услуг, 3 мастера с личными графиками, 3 клиентки, блокировки времени для проверки расчёта окон и несколько записей. Команду можно повторять: демо-данные перезаписываются заново.

В конце будет напечатана таблица «логин — пароль». **У каждой учётной записи свой случайный пароль**, и он показывается только здесь: нигде не сохраняется и второй раз не появится. Скопируйте её или запускайте команду заново — пароли при этом сменятся.

Без `SEED_SHOW_PASSWORDS` пароли не печатаются вовсе. Так и задумано для сервера: демо-записи нужны там как данные — мастера, к которым записываются, — а входить под ними не должен никто.

### 4. Запустить сервис

```bash
npm start
```

В ответ:

```
Сервис записи «Ноготочки» слушает http://127.0.0.1:3000
База: …/server/data/varvara.db
TLS: нет. Допустимо только на локальном стенде
Список адресов: http://127.0.0.1:3000/api
```

Окно не закрывайте — сервис работает, пока оно открыто.

### 5. Открыть в браузере

<http://localhost:3000>

Один процесс отдаёт и страницы, и API: всё, что начинается с `/api`, — это API, остальное — страницы из папки `web`. Так сделано не для простоты запуска, а потому что пропуск лежит в куке: кука привязана к источнику, и при разных портах браузер не прислал бы её вместе с запросом.

Открывать файлы из `web/` двойным щелчком бесполезно — из `file://` браузер не пустит их к API.

Страницы клиента:

| Адрес | Что это |
|---|---|
| `/` | лендинг: услуги, мастера, работы — всё из базы |
| `/login`, `/register` | вход и регистрация |
| `/password-reset`, `/password-change` | восстановление доступа и смена пароля |
| `/booking` | запись, шаг 1: выбор услуг |
| `/booking-master` | шаг 2: мастер или «любой свободный» |
| `/booking-time` | шаг 3: календарь и свободные окна |
| `/booking-confirm` | шаг 4: сводка, удержание окна, подтверждение |
| `/booking-done` | запись создана |
| `/account` | кабинет: активные записи и история |
| `/profile` | профиль: данные, напоминания, любимые мастера, согласия |
| `/bonuses` | абонементы и баллы |
| `/404`, `/500` | служебные страницы: не найдено и сервис не отвечает |
| `/appointment?id=…` | детали визита, отмена и перенос |
| `/sessions` | устройства и входы |
| `/notifications` | уведомления: что студия сделала с записями без участия клиентки |
| `/draft/admin.html` | черновая панель студии для проверки API — временная, до сборки админ-панели |

Панель студии, только для роли `admin`:

| Адрес | Что это |
|---|---|
| `/admin` | записи выбранного дня: сводка, фильтр по мастеру, отмена и перенос, оформление визита, блокировка времени |
| `/admin/services` | прайс: добавление, правка, включение и отключение услуг |
| `/admin/masters` | мастера и услуги, которые они выполняют |
| `/forbidden` | отказ в доступе для тех, у кого роли нет |

Интерфейс перестраивается под ширину экрана: сценарий записи проходится с телефона.

**Админ-панель и кабинет мастера появятся в следующей итерации.** Пока для них есть только черновая страница `/draft/admin.html`.

## Вход через Яндекс

Кнопка «Войти с Яндекс ID» стоит на экранах входа и регистрации. Человек
нажимает её, соглашается на странице Яндекса и попадает в свой кабинет —
пароль при этом не заводится вовсе.

Приложение регистрируется на <https://oauth.yandex.ru>, тип — «для авторизации
пользователей». Права нужны минимальные: адрес почты, логин, имя и фамилия.
Больше сервису от Яндекса ничего не требуется, а длинный список на экране
согласия отпугивает людей сильнее, чем помогает.

Три настройки, все из окружения:

| Переменная | Что это |
|---|---|
| `YANDEX_CLIENT_ID` | идентификатор приложения; не секрет, открыто уходит в адресную строку |
| `YANDEX_CLIENT_SECRET` | секрет приложения; **задаётся только в панели развёртывания** |
| `YANDEX_REDIRECT_URI` | адрес возврата, например `https://varvara-nails.ru/api/auth/yandex/callback` |

Без любой из трёх вход считается ненастроенным: сервер отвечает отказом,
а кнопка на странице не рисуется — кнопка, которая всегда отвечает отказом,
хуже отсутствующей.

**Адрес возврата Яндекс сверяет посимвольно** — протокол, домен, путь и косую
черту в конце. При несовпадении он не показывает ошибку, а молча уводит
человека по первому адресу из списка в кабинете. Поэтому строку в кабинете
и строку в `YANDEX_REDIRECT_URI` надо не набирать дважды, а копировать.

Что происходит по нажатию: сервис уводит человека на страницу согласия, тот
возвращается с одноразовым кодом, сервер меняет код на токен и токеном
забирает почту с именем. Дальше ищет человека по паре «сервис + идентификатор
Яндекса», затем по почте. Нашёл по почте — привязывает вход к тому же кабинету,
роли не меняет. Не нашёл — заводит новую клиентку без пароля. Пропуск выдаётся
собственный, тот же самый, что и при входе с паролем.

**Токен Яндекса нигде не сохраняется.** Он нужен на один запрос и подтверждает
ровно одно: человек владеет учётной записью в Яндексе. Хранить его — значит
отвечать за доступ к чужому аккаунту, а не запасаться на будущее.

Отказ на экране согласия и любая ошибка Яндекса возвращают человека на экран
входа с объяснением, а не на белую страницу.

Локально вход через Яндекс обычно не работает, и это ожидаемо: адрес возврата
указывает на боевой домен. Если нужно проверять на своей машине — заведите
второе приложение в Яндексе с локальным адресом возврата.

## Команды

Все запускаются из папки `server`.

| Команда | Что делает |
|---|---|
| `npm run migrate` | применяет новые миграции; уже применённые пропускает |
| `npm run seed` | загружает демонстрационные данные заново |
| `npm run reset` | удаляет файл базы и собирает её с нуля вместе с данными |
| `npm run doctor` | показывает версии, путь к базе, применённые миграции и целостность |
| `npm start` | запускает сервис: страницы и API на одном порту |
| `npm run dev` | то же, но с перезапуском при изменении файлов |

## Настройки

Файл `.env` **не обязателен**: без него всё работает на значениях по умолчанию. Если нужно что-то поменять — скопируйте образец и правьте копию:

```bash
cp .env.example .env
```

Файл `.env` в репозиторий не попадает: в нём место секретам, а им в истории не место. Незаполненные строки в копии не мешают — пустое значение считается незаданным, и берётся значение по умолчанию.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PORT` | `3000` | порт сервиса — и страниц, и API |
| `SQLITE_PATH` | `server/data/varvara.db` | путь к файлу базы от корня проекта |
| `SEED_SHOW_PASSWORDS` | пусто | `true` — напечатать пароли демо-записей при загрузке данных |
| `NODE_ENV` | `development` | в `production` сервер требует TLS |

Остальное — TLS, доверенный прокси, ограничение частоты, срок жизни сеанса — описано в `.env.example` и в [docs/deployment.md](docs/deployment.md).

## Если что-то пошло не так

**`Требуется Node.js 22.13.0 или новее`** — обновите Node. Проект использует встроенный SQLite, которого в старых версиях нет.

**`../.env not found. Continuing without it.`** — это не ошибка, а сообщение самого Node: файла настроек нет, работаем на значениях по умолчанию.

**`Порт 3000 уже занят другой программой`** — на 3000 сидит половина учебных проектов. Запустите на свободном:

```bash
PORT=3100 npm start
```

В PowerShell то же самое пишется иначе:

```bash
$env:PORT=3100; npm start
```

Тогда сервис откроется на <http://localhost:3100>. Надёжнее задать `PORT` в `.env` — не придётся помнить.

**`Не удалось удалить …varvara.db: файл занят другим процессом`** — `npm run reset` выполняется при работающем сервере. Остановите его (Ctrl+C) и повторите.

**`Слишком много попыток входа`** — сработало ограничение частоты: восемь неудачных попыток за 15 минут. Подождите или загляните в `.env.example`, там пороги настраиваются.

**Страница открылась, но данные не загрузились** — посмотрите окно, где запущен `npm start`: там видно каждый запрос и его код ответа. Сообщение об отказе страница показывает и сама, текстом.
